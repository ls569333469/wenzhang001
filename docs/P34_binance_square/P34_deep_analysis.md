你和同事的讨论归纳起来就是 **一个场景**：

> **每天对同一个项目持续产出不重样的内容，用于币安广场冲积分 / Kaito 嘴撸**

由此衍生的 4 个技术挑战：

| # | 挑战 | 对话中的描述 |
|---|------|------------|
| 1 | **每天不重样** | 历史去重（向量相似度检查），角度自动轮换 |
| 2 | **实时数据** | 爬虫/搜索拿项目最新动态（官网、X、CoinGecko） |
| 3 | **人味问题** | 币安广场反 AI 检测严，纯投研风格被打低分 |
| 4 | **工具解耦** | 爬虫系统 vs 写作系统是否分开 |

## 三、关键判断 — 对话中的建议 vs 我们的实际情况

### 1. 关于爬虫/数据采集

> 对话建议：需要 Playwright/BeautifulSoup 爬虫 + Unstructured.io 清洗

**我的判断：我们不需要另建爬虫系统。**

理由：
- 我们已有 **Surf API**（Scout 流程每天调用），能实时搜索项目最新资讯
- 我们已有 **Google Sheets 数据源**（媒体文章清洗片段）
- 我们已有 **浏览器子Agent**（Playwright，用于截图）
- 对话中的方案假设是从零开始 build，但我们有成熟的数据管线

**结论：复用 Surf API 做"项目实时搜索"，不需要独立爬虫工具。**

### 2. 关于向量存储

> 对话强推 Chroma + bge-small-zh-v1.5

**我同意需要加向量存储，但有分歧：**

- 对话建议直接在 Python 环境 pip install chromadb → 这在我们的 FastAPI 后端里完全可行
- 但**是否需要全量索引历史 MD 报告**？我认为不需要
- 更实际的做法：**只索引"已发布内容"的摘要**（项目名+角度+摘要+日期），轻量级几百条就够
- 嵌入模型选择：可以直接用我们现有的 LLM API 做 embedding，不一定要本地跑 HuggingFace 模型

### 3. 关于"爬虫和写作分两个工具"

> 对话建议：分开做两个独立工具

**我的判断：在我们的架构里不需要刻意分开。**

理由：
- 我们的 Pipeline 已经是 **Step 分离** 的（Scout→Strategist→Writer→...每步独立）
- 数据采集（Scout/Surf）和内容生成（Writer/Polisher）本来就是独立 Step
- 一个出错不影响另一个（有日志+错误重试机制）
- 硬拆成两个工具反而增加维护成本和前端复杂度

**结论：保持现有单管线架构，通过 Step 隔离实现解耦。**

### 4. 关于 0.78 死循环问题

> 对话担心向量相似度检查导致死循环

**我们已有完善的防护模式：**
- Critic 已有 `max_revisions: 1-3` 限制
- 只需给去重检查加同样逻辑：**最多重试 3 次，第 3 次强制放行+标记**
- 额外安全：角度列表预生成 5 个，用完即止，不做无限重试

## 五、修正后的架构方向

```
                    ┌─────────────────────────┐
                    │    向量历史库 (Chroma)     │
                    │  存: 项目+角度+摘要+日期   │
                    └──────────┬──────────────┘
                               │ 查询/写入
        ┌──────────────────────┼──────────────────────┐
        │                      │                      │
   ┌────▼─────┐         ┌─────▼──────┐        ┌─────▼──────┐
   │ 角度推荐  │         │  去重检查   │        │  历史存储   │
   │(5个不重样) │         │(cosine<0.78)│        │(生成后保存) │
   └────┬─────┘         └─────┬──────┘        └────────────┘
        │                     │
   ┌────▼─────────────────────▼──────────────────┐
   │          现有 Agent 管线                      │
   │  Surf搜索 → Strategist → Writer → Polisher  │
   │  (数据采集)   (策略)      (写作)    (润色)     │
   └──────────────────────────────────────────────┘
```

共享基础设施，上层通过 **模式配置** 区分行为：
- `kaito_yap` → 短帖、犀利、Degen 风格、跳过审核
- `binance_square` → 结构化、合规、带标签、需审核
