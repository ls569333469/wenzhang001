# P26 刻板句式 & AI 指纹解决方案

> 日期：2026-02-18
> 背景：25 篇综合审核发现「就像」出现 29 次/19 篇、「，而是」出现 23 次/17 篇，形成跨文章 AI 指纹
> 根因：Writer prompt 中的「比喻」指导区块激活了 LLM 对明喻句式的注意力

---

## 一、问题诊断

### 1.1 直接原因

Writer prompt 第 52-55 行：

```
## 比喻（不强制，用的话注意）
- 如果用比喻，**禁止从赌博（筹码/牌桌）和战争（战场/猎杀/阵地）取材**
- 多从日常生活找：做饭、交通、天气、运动、装修、看病
```

虽然标注「不强制」，但：
1. **出现即激活**：LLM 对 prompt 中提及的任何概念有强烈的执行倾向
2. **给了取材范围**：等同于鼓励使用比喻
3. **默认连接词**：Gemini 做中文比喻时默认使用「就像」

### 1.2「，而是」的来源

Writer prompt 第 19 行：`不是改写原文，而是用自己的视角`

LLM 将这种「不是 A，而是 B」的对比结构学习为写作套路，频繁复制到正文中。

### 1.3 核心认知

> **"不要想粉色大象" 效应**：在 prompt 中提到任何概念（无论肯定还是否定），都会激活 LLM 对该概念的注意力。说「不要用比喻」依然在提醒模型「比喻」的存在。最有效的做法是**完全不提**。

---

## 二、解决方案（按优先级排序）

### 方案 1：删除比喻指导区块 + 禁用词迁移（P0 — 立即生效）✅ 已确认

**做法**：
1. 直接删除 Writer prompt 的 `## 比喻` 区块（第 52-55 行 + 分隔线），不留任何替代文字
2. 将原区块中的禁用比喻词（筹码、牌桌、战场、猎杀、阵地）迁移到 `forbidden_patterns.yaml`，由 Polisher 代码扫描拦截
3. Writer prompt 第 19 行 `不是改写原文，而是用自己的视角` → 改为 `用自己的视角重新构建一篇原创短文`

**原理**：
- 不提即不激活——LLM 在没有比喻提示的情况下，会根据表达需要自然决定用不用比喻
- 禁用词保障从 prompt 层面转移到代码层面（Polisher），更可靠

**改动量**：删 5 行 prompt + 改 1 句 + forbidden_patterns.yaml 增加 5 个词
**预期效果**：「就像」出现率从 79%（19/24 篇）降到自然水平（预估 20-30%）

---

### 方案 2：Few-shot 范文引导 ❌ 暂不可行

**做法**：精选 2-3 篇人味最浓、句式多样的标杆文章，通过 `rag_context` 固定注入 Writer prompt。

**暂缓原因**：Web3 领域缺少固定的优质文章作者，内容多为信息差驱动。当前范文来源是借鉴 Web2 博主的内容生成的 Google 表单，不适合直接作为 Few-shot 范文固定注入。

**后续考虑**：如果未来积累了足够多的高质量生成文章，可以从中精选作为范文。

---

### 方案 3：角色人设具象化（P1 — 增强人格差异）✅ 已确认

**现状**（Writer prompt 第 16-17 行）：
```
你是Web3+AI领域天天泡在链上的独立创作者，在X上有固定读者群。
看到事情忍不住要说两句的老玩家。
```

**问题**：角色描述过于泛化，LLM 容易回退到通用写作模板。

**优化方向**：增加具体经历和专业背景描述（不加缺陷/口头禅），让人设足够具体以减少通用模板输出。

**候选方案**：

方向 A — 经验型（强调阅历深度）：
```
你在链上待了6年，从DeFi Summer、NFT狂潮到铭文热一路经历过来。
现在在X上写独立评论，读者主要是中文圈的链上活跃用户和交易员。
你关注宏观政策、链上数据和项目基本面，习惯从数据出发形成判断。
```

方向 B — 媒体人型（强调表达风格）：
```
你是一个从财经媒体转行到Web3的独立评论人，在X上写中文短评。
你的读者群是对宏观经济和链上资产都感兴趣的中文用户。
写作节奏快，信息密度高，喜欢用一手数据和具体案例支撑观点。
```

方向 C — 最小改动（保留原有调性）：
```
你是Web3领域的独立创作者，在X上用中文写短评，读者是链上活跃用户。
从2019年入圈至今，经历过多轮牛熊，对市场周期和叙事切换有体感。
```

**状态**：待用户选择方向

**原理**：越具体的人设 → LLM 越难回退到通用句式 → 自然减少刻板表达

**改动量**：改 2-3 行角色描述
**预期效果**：不同素材的文章风格差异度提高

---

### 方案 4：Polisher 高频句式检测（P2 — 兜底保障）❌ 暂不更新

**做法**：在 Polisher 的 `code_pre_scan` 阶段增加句式频率检测，超频时注入改写指令。

**暂缓原因**：效果不确定，先观察方案 1+3 实施后的效果再决定是否需要此兜底机制。

**局限**：只能控制单篇内频率，无法解决跨文章的句式雷同问题。

---

### 方案 5：修辞随机化（P2 — 可选增强）

**做法**：在 Polisher 代码层面，对检测到的高频句式随机决定是否替换，将替换建议注入 LLM 改写指令。

```python
ALTERNATIVES = {
    "就像": ["相当于", "无异于", "活脱脱是", None],  # None = 改为暗喻
    "，而是": ["，但实际上", "——", None],  # None = 直接陈述
}
if random.random() < 0.6:  # 60% 概率触发替换
    alternative = random.choice(ALTERNATIVES[pattern])
    inject_instruction(f"将「{pattern}」替换为其他表达方式")
```

**原理**：即使单篇看正常，批量看同一句式出现率从 100% 降到 ~40%。

**适用场景**：单篇生成模式下，跨文章的多样性控制。
**改动量**：Polisher 增加随机化逻辑
**预期效果**：跨文章的句式重复率降低 50-60%

---

### 方案 6：Temperature 提高（P3 — 谨慎使用）

**做法**：将 Writer 的 temperature 从当前值提高到 0.9-1.0。

**原理**：更高的随机性 → 更多样的词汇选择 → 减少模板化输出。

**风险**：
- 可控性降低
- 可能增加事实错误
- 可能产出更多需要 Critic/Polisher 纠偏的内容

**建议**：仅在方案 1-4 效果不足时考虑，且需配合更严格的 Critic 审核。
