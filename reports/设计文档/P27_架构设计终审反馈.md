# P27 架构设计终审反馈：提升空间与不足之处

> 角色：前端/全栈架构师
> 目标：基于 P27 现有设计文档与 Mockup，进行编码前的最后一次风险排查与优化建议（不涉及代码修改）。

整体来看，P27 是一个**方向极其正确、审美在线、且敢于舍弃历史包袱（砍掉无效 UI 和页面）的优秀迭代方案**。特别是方案 B 的“左右分栏”设计，彻底释放了宽屏生产力。

但在我反复推敲前后端数据流、React 状态管理以及端到端的用户体验后，我认为 P27 方案在实际落地时，还存在以下 **3 个不足之处（隐患）与提升空间**，需要你在心里有个底：

---

## 🛑 不足之处 1：DataPanel 的“无米之炊”（严重级）

*   **现状**：设计图里画了极其精美的 `BullishFeed`（推文时间线）和 `KaitoBoard`（项目情报看板），上面布满了头像、点赞数、新闻卡片。
*   **隐患**：根据之前的交接报告，**目前后端根本没有接通 Grok API 或 Surf API**。现有的数据流严重依赖极其有限的 Google Sheets（并且需要手动更新）。
*   **带来的灾难**：如果你要求我（前端开发）立刻像素级还原这个 DataPanel，我会因为**后端没有提供这些丰富结构的数据结构（Schema），而不得不写死大量的假数据（Hardcode）**。这会导致 P27 表面上完工了，但实际上是一个空壳，一到 P28 换成真接口，前端需要推倒大部分取值逻辑重来。
*   **优化建议**：
    *   **后端先行或强约束 Mock**：在开发 DataPanel 前，必须先让后端定死返回的 JSON 结构。前端严格按照契约写，即使数据是 Mock 的，数据骨架也不能变。
    *   **降级方案**：如果 Grok API 短期内拿不到头像、点赞数这种花哨字段，UI 上必须准备好一套“只有纯文本推文”的降级版 Feed 流样式，避免上线时页面因字段缺失而崩溃。

## 🛑 不足之处 2：Data Panel 与 Configuration 的状态隔离

*   **现状**：左边 `ConfigPanel` 选模式（吹捧/Kaito），中间 `DataPanel` 渲染对应的 Feed/看板。
*   **隐患**：在传统的 React 设计中，往往会把这两个面板写成两个平行的组件。当你在右边选了一篇推文点击“引用”时，左边的 Config （比如自动把字数调短）应该怎么反应？目前的设计图里，我们**只看到了视觉上的分离，没有看到状态（State）联动的定义**。
*   **优化建议（技术实现层面）**：
    *   必须在 `Zustand store (useAgentStore)` 里建立一个统一的 `CreationContext`。无论你是点左边的配置，还是点中间资料面板里的“采纳”，都必须更新到同一个全局 Store。千万不能让各个 Panel 各自维护本地的 useState，否则会导致最后写进编辑器的数据是错乱的。

## 🌟 提升空间 1：更智能的 Empty State 与引导 (UX 提升)

*   **现状表现**：目前的设计图假设用户一进来，币安动态（Feed）就已经刷刷刷加载好了。
*   **提升空间**：当用户第一次进入这个系统，或者后端去抓数据需要 5 秒钟时，用户看到的是什么？目前的文档里没有定义加载中（Loading Skeletons）和无数据（Empty State）的优雅状态。
*   **优化建议**：
    *   为 `BullishFeed` 加上骨架屏（Skeleton）加载动画。
    *   为 RightSidebar 的“进度”时间轴，在空闲状态下增加一个“随时待命，开始创作吧”的友好空提示加载页（前面提到过，这非常重要）。

## 🌟 提升空间 2：模式切换过程中的“画布污染”问题

*   **现状场景**：假设我现在正在用“吹捧模式”写作，富文本里写了 500 字。突然，我在左侧 ConfigPanel 点了“投研模式”。
*   **隐患反思**：这时候，中间的 DataPanel 瞬间从推文变成了股票搜索框，但是**右侧富文本框里的那 500 字吹捧文，是保留还是清空？** 如果保留，它与当前“投研”的上下文完全冲突；如果清空，用户可能会因为误触而丢失大量文字。这就是典型的“模式切换引发的数据灾难”。
*   **优化建议**：
    *   在左侧切换【模式】时，执行**强校验**：如果当前编辑器内有未保存的内容，弹出一个优雅的确认窗（或者非侵入式的 Toast 警告）：“切换模式将清空当前画布，是否先保存草稿？”。
    *   结合 P27 刚做好的本地保存功能，可以自动给用户存一个临时草稿，再执行清空并切换 DataPanel 的动作。

---

### 总结意见

P27 的外壳（UI 和交互层级）我已经可以打 95 分。
剩下的 5 分，全部在于**异常处理（无数据、正在加载、意外切换）**以及**应对后端基建薄弱时的优雅降级**。

如果你觉得没问题，我们的下一步就可以直接进入 P0 阶段的技术清理，以及开始在后端配合下搭建这些核心的 UI Store 结构了。

---

## 团队讨论结论（2/20）

| # | 反馈 | 结论 | 处理方式 | 额外工作量 |
|---|------|------|---------|-----------|
| 🛑 1 | DataPanel 无数据源 | **不是问题** | DataPanel 只需文本内容（和现有素材爬取一样），不需要头像/点赞等社交指标。现有 Google Sheets 数据完全够用，不依赖 Grok/Surf API | **0** |
| 🛑 2 | 状态隔离 | **采纳** | `useAgentStore` 新增 `selectedMaterial` + `isDirty` 字段，三面板共享统一 Store | P1 顺带做 |
| 🌟 3 | Empty State | **采纳** | DataPanel 加载时显示 Skeleton 骨架屏，无数据时显示友好空状态。使用 shadcn 现有 Skeleton 组件 | P1 顺带做 |
| 🌟 4 | 模式切换污染 | **采纳** | `setMode()` 判断 `isDirty`，有未保存内容时自动存草稿 + Toast 提示（非侵入式），不用 Modal 弹窗 | P1 顺带做 |

**总结**：4 条反馈中 3 条采纳，均不需要额外排期，在 P1 阶段实现 DataPanel 时顺手解决。
