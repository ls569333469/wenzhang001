# P29 提示词优化设计文档 — 经验总结

> 日期：2026-02-22
> 风格：banfo（半佛仙人）
> 目的：记录 P29 提示词优化过程中的经验和教训，供后续其他风格优化复用

---

## 一、目标与背景

将 short_article 模式的输出从"AI分析式文章"优化为"X KOL 风格的即时评论"。核心问题：开头像分析报告、缺少口语感、风格不像真人。

---

## 二、最终采纳方案（B方案）

### 架构

```
Google Sheets（半佛15,214条样本）
  ├── pattern_menu: 提取 top15 逻辑公式 → 传给策略师选
  └── random 样本 3条 → 策略师看风格感
                    2条 → 写手学语感

策略师（选题方向 + hook）
  ↓ JSON: label/angle/hook/logic_pattern/tone
写手（按方案写文）
```

### 关键代码改动（6个文件）

| 文件 | 改动 |
|------|------|
| `strategist/short_article.jinja2` | hook描述改为"参考样本风格"、加 `{{ rag_context }}`、思维工具约束 |
| `strategist.py` | 注入 `pattern_menu` + 样本到上下文 |
| `writer/short_article.jinja2` | 输出结构加"即时反应写第一句" |
| `writer/short_article.py` | user prompt 传 `logic_pattern`、"即时反应" |
| `google_sheets_source.py` | `get_pattern_menu()`、修复 `get_samples()` style 过滤 bug |
| `sample_service.py` | 透传 `get_pattern_menu()`、`get_targeted_samples()` |

## 三、测试历程与教训

### 教训1：改下游没用，必须改源头

| 轮次 | 改了什么 | hook 效果 |
|------|---------|----------|
| 1 | 只改写手模板（加口语化引导） | ❌ 分析式 |
| 2 | 改策略师模板（公式菜单）但没改 hook 描述 | ❌ 分析式 |
| 3 | 改策略师 hook 描述 → "不要写分析式陈述" | ✅ 口语反应式 |

**结论**：写手的开头完全由策略师的 hook 决定。hook 字段说"判断或信息" → 出来就是分析式。改成"参考样本风格，不要写分析式陈述" → 立刻变好。

### 教训2：模板渲染必须验证

策略师模板里有 `{{ rag_context }}` 占位符吗？没有！导致代码费力取了样本，但策略师的 prompt 里根本没出现。

**检查清单**：改 context 之前，必须先确认模板里有对应的 `{{ 变量 }}`。

### 教训3：字段描述 > 样本暗示

即使给策略师看了"是时候成为大肌霸了"这样的口语化开头样本，但 hook 字段描述写的是"判断或信息"，策略师依然写出分析式 hook。

**结论**：字段描述（显式指令）的影响力远大于样本（隐式暗示）。

### 教训4：思维工具会被混用

策略师模板里"思维工具"和"公式菜单"两个区块挨太近，策略师会把思维工具的词（换主体、反过来想）当成 `logic_pattern` 输出。

**修复**：在思维工具标题加"严禁作为 logic_pattern 输出"。

### 教训5：测试脚本必须严谨

- B 组说是 random 样本 → 实际调用的代码已经改成精准匹配 → 两组无区别
- 每次测试用同一篇素材 → hook 雷同，误以为模板固化
- PowerShell 输出乱码 → 应输出到文件

**检查清单**：
1. B 组必须手动构建上下文绕过代码改动
2. 每组测试必须记录完整的 system prompt + user prompt
3. 至少用 2 篇不同素材验证

## 五、B vs C 方案对比结论

### B方案：Random 样本（当前采用）

**流程**：从 Google Sheets 随机取样本，不按类型或公式筛选。

```
策略师:
  1. 从 Google Sheets 随机取 3 条样本（可能是正文段落、开头金句、行动号召混着来）
  2. 样本出现在策略师 prompt 的「风格参考样本」区块
  3. 策略师参考样本的语感 + hook 字段描述（"不要写分析式"），写出 hook
  4. 从公式菜单（top15）为每版本选一个 logic_pattern

写手:
  5. 从 Google Sheets 随机取 2 条样本（3个版本共用）
  6. 照搬策略师的 hook 当开头
  7. 按 logic_pattern 组织正文
```

**示例**（IoTex 素材）：
```
策略师随机样本:
  样本1 [正文段落][对比论证+比喻]: "人生不就贵在多试错嘛..."（讲人生哲理的）
  样本2 [正文段落][时间对比]: "我再年轻5岁都会不屑一顾..."（讲感悟的）
  → 跟 IoTex 黑客话题完全无关，但 LLM 从中学到了"半佛"的语气

输出 hook: "200万美元买个教训，这IoTex也太贵了！"
输出 V2 hook: "币圈一天，人间一年。IoTex这波啊，属于是考古项目诈尸了…"
```

---

### C方案：精准样本匹配（备选，待标签统一后启用）

**流程**：按 snippet_type 和 logic_pattern 精准筛选样本，策略师和写手共享同一套开头金句。

```
策略师:
  1. 精准取 2 条「开头金句」+ 1 条「行动号召」样本
  2. 样本出现在策略师 prompt 的「风格参考样本」区块
  3. 策略师参考样本的语感写 hook，从公式菜单选 logic_pattern

写手（每版本独立取样本）:
  4. 取策略师看过的同一条「开头金句」（共享，保证风格一致）
  5. 按策略师选的 logic_pattern 精准取 1 条匹配的「正文段落」
     例：策略师选了"类比论证" → 取一条 logic_pattern 含"类比论证"的正文样本
  6. 写手看到的开头样本和策略师一致，正文样本和公式一致
```

**示例**（IoTex 素材）：
```
策略师精准样本:
  开头金句1 [现象洞察]: "我最近还发现一个很有趣的现象..."
  开头金句2 [悬念设问]: "微信步数藏了多少人情世故"
  行动号召1 [因果论证]: "正因为这个世界上没有一定能赢的制胜法..."

V1 写手样本（策略师选了"类比论证"）:
  开头金句: 与策略师相同 → "我最近还发现一个很有趣的现象..."（共享）
  正文段落 [类比论证]: "夜店酒水贵，又吵又闹，为什么那么多人去？"（按公式匹配）

输出 hook: "200万刀的教训，够不够买一份全链安全指南？"
输出正文: "就像一辆高速行驶的汽车，哪怕只有一个螺丝松动..."（确实用了类比）
```

---

### 对比总结

| 维度 | B（random） | C（精准） |
|------|-----------|---------|
| **策略师看什么样本** | 随机 3 条（可能全是正文段落） | 精准：2 开头金句 + 1 行动号召 |
| **写手看什么样本** | 随机 2 条，3 版本共用 | 每版本独立：1 共享开头 + 1 按公式匹配正文 |
| **策略师-写手样本一致性** | ❌ 各自独立随机 | ✅ 共享同一条开头金句 |
| **Hook 质量** | ⭐⭐⭐⭐ 靠约束兜底就够好 | ⭐⭐⭐⭐ 略好但差距不大 |
| **正文公式执行** | ⭐⭐⭐ LLM 自由发挥 | ⭐⭐⭐⭐ 有对应公式的样本参考 |
| **代码复杂度** | 低（2次取样） | 高（策略师3次+每版本2次=9次取样） |
| **数据依赖** | 不依赖标签一致性 | 高度依赖（标签不一致时退化为 random） |
| **当前问题** | 无 | logic_pattern 标签粗细不一致 |

**决策**：现阶段采用 B 方案。待 Google Sheets 的 logic_pattern 标签统一后（"类比论证+比喻" → "类比论证"），再切到 C 方案。

## 六、其他风格优化复用清单

1. **先改策略师模板的 hook 描述** — 这是效果最大的单点改动
2. **确认 `{{ rag_context }}` 在模板中渲染** — 否则样本白取
3. **运行 `get_pattern_menu()` 检查公式菜单** — 确认该风格有足够的 logic_pattern 标注
4. **检查 `get_samples()` 是否能正常返回** — 排除 style 过滤问题
5. **至少用 2 篇不同素材测试** — 避免素材本身导致 hook 雷同
6. **测试脚本记录完整 prompt** — 策略师 system/user prompt 和写手 user prompt 都要记录
7. **检查思维工具是否混入 logic_pattern** — 确认约束语生效

# P30 提示词优化经验总结 — 吹捧模式（bullish_take）

> 日期：2026-02-24
> 目的：记录 P30 吹捧模式从A方案→B方案的完整优化过程，提炼可复用的方法论

---

## 一、问题诊断方法：先拆解标杆，再对照自己

### 1.1 拆解真实标杆

不是凭感觉改提示词，而是先**拆解25篇CZ实际转发的推文**，归纳出5种被转发的内容模式：

| 模式 | 占比 | 核心逻辑 |
|------|------|---------|
| 摆数据 | 20% | 用客观数据碾压，不争辩 |
| 做了再说 | 28% | 先行动，币安只是背景 |
| 翻译价值 | 16% | 把业务新闻翻译成投资者能理解的利好 |
| 深度搬运 | 12% | 长内容→要点提炼 |
| 产品体感 | 24% | 用户视角说好在哪 |

### 1.2 对照现有模板

把标杆模式和当前模板对照，发现3个结构性问题：

| 标杆特征 | 当前模板的做法 | 问题 |
|---------|-------------|------|
| 主角不是币安 | "选一种夸法夸币安" | ❌ 币安是主角 |
| 有独立信息量 | 只复述素材数据 | ❌ 没有翻译/升维 |
| 姿态是同路人 | "币安合作KOL" | ❌ 像下属 |

**方法论**：**先拆解标杆→归纳模式→对照现有模板→找结构性差距**，不要一上来就改提示词。

---

## 二、核心方法论：从"禁止做X"到"引导做Y"

### 2.1 A方案（禁止型）的失败

A方案的策略师用"4种夸法"（夸决策/夸成果/夸格局/夸执行力），本质是在告诉LLM"从哪个角度夸币安"。无论怎么加禁止项，输出都是**评价者视角**——因为任务本身就是"夸"。

### 2.2 B方案（引导型）的成功

B方案把"4种夸法"（praise_type）换成"5种切入视角"（perspective），从根本上改变了LLM的思考方向：

```diff
 A方案：praise_type → "夸决策" → LLM思考"币安的决策好在哪"
+B方案：perspective → "讲体感" → LLM思考"我用了之后什么感受"
```

**方法论**：**当"禁止做X"反复失败时，换成"引导做Y"**。LLM对正面指令的遵从度远高于负面约束。

### 2.3 关键字段变更对照

| A方案字段 | B方案字段 | 变化 |
|----------|----------|------|
| `praise_type`（夸什么） | `perspective`（切入视角） | 从评价者→叙事者 |
| `angle`（切入角度） | `story`+`detail` | 拆分为故事线+事实抓手 |
| 无 | 核心原则"读者是主角" | 新增顶层原则 |

## 三、字数控制方法论

### 3.1 三种控制手段的效果对比

| 手段 | 原理 | 实测偏差 | 结论 |
|------|------|---------|------|
| **提示词描述** | "请写约200字" | +60%~+113% | ❌ 不可靠，LLM话痨倾向无法克服 |
| **max_tokens硬限制** | API层面截断 | +17%~+44% | ⚠️ 有效但太紧会截断结尾 |
| **提示词+token双控** | 提示词引导方向 + token做兜底 | +17%~+35% | ✅ 最佳组合 |

### 3.2 最终方案

```
提示词：user_prompt 中只写一次字数要求（避免system/user冲突）
Token：max_tokens = target × 2（给足空间不截断）
范围：250-500字，target 350（LLM在350+区间控制最稳定）
```

### 3.3 策略师定字数（实验后放弃）

曾尝试让策略师为每个版本指定不同的 `target_length`（如150/300/450），实测发现：
- 300字以上的目标控制合理（偏差16-22%）
- 200字以下的目标严重超标（+79%~+113%）
- LLM的表达惯性在短篇幅时无法克服

**结论**：策略师定字数方案适合300+字的场景，短篇场景无效。最终改为统一字数。

## 四、四模板对齐原则

### 4.1 问题：禁用词不一致

写手禁止了"赛道/生态/布局"等AI词，但审核师和润色师的禁止清单里没有这些词，导致审核可能放过、润色可能引入这些词。

### 4.2 方法论：四模板必须共享同一套标准

```
策略师 → 定字段（perspective/story/detail/tone/logic_pattern）
写手   → 用字段写作 + 遵守禁止清单
审核师 → 按字段逐项检查 + 同一套禁止清单判定
润色师 → 保持字段一致 + 同一套禁止清单过滤
```

**具体对齐清单**：

| 检查项 | 策略师 | 写手 | 审核师 | 润色师 |
|--------|--------|------|--------|--------|
| 核心原则 | ✅ 定义 | ✅ 遵守 | ✅ 检查 | ✅ 保持 |
| 禁用词 | — | ✅ 列出 | ✅ 同一份 | ✅ 同一份 |
| perspective | ✅ 输出 | ✅ 按此写 | ✅ 检查是否体现 | — |
| story | ✅ 输出 | ✅ 按此写 | ✅ 检查是否体现 | — |
| detail | ✅ 输出 | ✅ 按此写 | ✅ 检查是否用到 | ✅ 不删除 |
| tone | ✅ 输出 | ✅ 按此写 | ✅ 检查是否偏离 | ✅ 保持 |
| 节奏要求 | — | ✅ 定义 | ✅ 检查 | ✅ 保持 |

### 4.3 Python代码的对齐bug

`standard_critic` 始终取 `plans[0]` 的字段，但审核版本2时应该取 `plans[1]`。新增 `variant_index` 参数修复。

**方法论**：代码层面的字段传递也要和模板对齐，不能只改模板不改代码。

## 六、P30 可复用清单

1. **先拆标杆再改提示词** — 拆解真实的好内容，归纳模式，对照差距
2. **"禁止做X"失败时换成"引导做Y"** — 正面指令 > 负面约束
3. **一个原则只在一处定义** — 字数只在user prompt说一次，避免system/user冲突
4. **字数用提示词+token双控** — 提示词引导方向，max_tokens做兜底
5. **四模板共享同一套标准** — 禁用词、检查项、核心原则全部对齐
6. **代码字段传递要和模板对齐** — 改了模板的字段名，必须同步改Python
7. **测试用不同素材** — 至少2篇不同类型素材（数据型 vs 产品型），验证泛化能力
